# 1.21.1 visual compatibility and NeoForge preparation

## Source boundaries

- `src/main` and `src/client` contain loader-neutral gameplay and visual code where possible.
- `src/compat/legacy` contains Minecraft 1.21.1 implementations for APIs replaced by the 1.21.2 render-state rewrite.
- `com.kingdomcomecombat.platform` is the loader boundary. Fabric-specific implementations live below its `fabric` package; a NeoForge build should provide equivalent services without changing consumers.

## 1.21.1 visual migration order

1. Player lock-on body/head orientation and first-person safety.
2. Player held-item, armor overlay, blood and bandage render hooks.
3. Zombie, skeleton, piglin and illager combat animation models.
4. Render-state-only hit reactions and model hurtbox tracking.

### Restored in the first visual pass

- entity bloodied body textures;
- bloodied/damaged armor textures;
- data-driven combat poses for zombies, skeletons, piglins and illagers;
- special first-person body rendering with hidden head, shader shadow-pass handling and configurable forward offset;
- isolated development run directories per Minecraft target.

Each restored feature should be implemented in `src/compat/legacy`, selected only when `target_mc` predates 1.21.2, and tested with both `1.21.1` and the default target.

## NeoForge port boundary

The first loader-neutral services are:

- configuration directory lookup;
- optional-mod detection.

The next APIs to move behind platform adapters are, in order:

1. networking registration and packet send;
2. server/client tick and lifecycle callbacks;
3. resource reload listeners and commands;
4. HUD/world-render callbacks and key registration;
5. item, entity, particle and sound registration.

Do not duplicate combat rules in a NeoForge source set. Only loader registration, events, networking transport and compatibility hooks should differ by loader.
